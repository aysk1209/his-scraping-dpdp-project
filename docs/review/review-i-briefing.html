What we built, and how to defend it

Every file, the whole pipeline, the exact scoring arithmetic, and the answers to the questions the panel is most likely to ask. Written for someone who has never seen the code.

7 DPDP rules 3 techniques 91 tests passing ~1,900 lines Python 0 models trained

01The short version

If you only remember one paragraph, remember this one.

Hospitals hold extremely sensitive data. There are many published techniques for pulling data out of hospital systems, and they are all judged on the same three things: how fast they are, how much they capture, and how well they survive a page redesign. Nobody scores them on whether the extraction was lawful.

We built the missing instrument. It takes any extraction run, checks it against seven principles from India's Digital Personal Data Protection Act 2023, and returns a single number between 0 and 1 — plus a written reason for every mark lost. Because it is the same instrument every time, two different extraction techniques can finally be compared on compliance the way they are already compared on speed.

Say this

“Existing scrapers are benchmarked on speed, coverage and robustness. We add a fourth axis — data-protection compliance — and we make it a number, produced by one shared harness, so techniques can be ranked on it.”

The demo shows three extraction techniques attempting the same three jobs against the same hospital data. They differ only in how they treat personal data. The instrument separates them cleanly:

TechniqueScoreRules passedWhat it does
Compliance-aware (ours)1.0007/7Pulls only the fields the job needs, files a full manifest
Minimising, undocumented0.5002/7Pulls only what it needs, but does no paperwork
Unconstrained (baseline)0.1310/7Ignores the job, scrapes every field it can reach

The middle row is the one worth pointing at. It proves the instrument is measuring more than “did you grab too much data” — that technique passes data minimisation outright and still loses half its marks, because it never recorded a lawful basis, a deletion route, a privacy notice or an audit trail.

02There is no AI in what we are demonstrating

This is the single most important thing to get right on the day. Say it before you are asked.

Do not get caught out

Nothing in the demo is trained. There is no model, no dataset of labelled examples, no neural network, and no API call to any language model. src/agent/ contains a docstring and nothing else. Every number on screen is produced by ordinary Python — set arithmetic, boolean checks and an average.

At Review-1 the panel asked how we are “training” the agent. That question came from our own slide, which said the agent would be “trained and validated” on the hospital system. That wording was wrong, and correcting it is the honest answer:

  • Nothing is trained. No fine-tuning, no weights, no training data, no GPU.
  • The language model comes later and does a different job. In build step 6 an off-the-shelf model (Claude, via the Anthropic API) will be used to find and pull data out of unfamiliar hospital screens. It will never be the thing that decides a compliance score.
  • What replaces “training” is prompt design, tool design and evaluation. We give the model instructions and a fixed set of actions it may take, then measure how well it does against synthetic data we control.

Why the scorer deliberately is not an AI

This is a design decision to defend, not a gap to apologise for. A benchmark has to be reproducible: the same run must produce the same score today, next month, and in a reviewer's hands. A language model gives slightly different answers to the same question, so a model-scored benchmark could not be replicated — and a number nobody can reproduce is worthless as evidence in a paper.

It also has to be auditable. Every mark our harness deducts points at a specific line of code and prints a sentence saying why. “The model judged it non-compliant” is not something you could ever put in front of a regulator or a hospital's data protection officer.

Say this

“The scorer is deliberately deterministic, not learned. A compliance benchmark has to be reproducible and auditable — every deduction traces to a rule and prints its reason. The language model belongs in the extraction stage, where the problem is genuinely open-ended, not in the measurement stage.”

03The pipeline, stage by stage

Six stages. Data is manufactured, pulled, tagged, judged, scored and compared.

0
Define the vocabulary

Before anything runs, the code fixes what words mean. A hospital system is modelled as five layers (patient admin, clinical records, departmental systems like lab and imaging, billing, and the infrastructure that joins them). Every piece of data belongs to one of six categories: direct identifier, quasi-identifier, clinical, financial, administrative, contact.

That category is the unit everything downstream reasons about — never the hospital's own field names. This is what makes the work portable across different hospital systems.

1
Manufacture the data

We have no live hospital access, so we generate our own records. A catalogue lists every field that exists in each layer and what category it falls into — mrn is a direct identifier, primary_diagnosis is clinical, billed_amount is financial. A generator then invents plausible values for those fields using Faker, seeded so the demo produces identical output every run.

Five records per layer across four layers. No real patients, no real hospital.

2
Pull the data

Everything downstream talks to one interface, HISDataSource, which offers exactly two things: which layers exist, and give me records from a layer. Today the synthetic generator sits behind it. When credentialed hospital access arrives, a real browser-automation scraper sits behind the same interface and nothing else in the codebase changes.

The live version already exists as a file that deliberately refuses to run — proof the boundary is real rather than promised.

3
Apply a technique

A task says what someone wants: an identifier, a date of birth, a diagnosis, a medication list — and the lawful purpose for wanting it. A technique is a strategy for satisfying that task. Three exist, and they behave differently on purpose.

Critically, each technique also files its own manifest: the purpose, the lawful basis, how long data is kept, how it gets deleted, what security is in place, whether patients were given notice, and who is accountable. Compliance is something the technique produces about itself, not a label we bolt on afterwards.

4
Judge it

Seven rules read the manifest and the pulled records. Each returns pass or fail, a score from 0 to 1, and plain-English findings. They check against a policy table that states, for each purpose, which categories are necessary, the maximum retention, and whether identifiers must be pseudonymised.

Keeping that policy in one editable table means tuning the compliance envelope is a configuration change, not a code change — which is exactly what an auditor would want.

5
Score and compare

The seven rule scores collapse into one number, and the result is written out three ways: a console table for the demo, JSON for machines, and Markdown to paste into the report. The benchmark repeats this for every technique against every task and ranks them.

04What the inputs actually are

Expect “where does your data come from?” — there are three inputs, and two of them are configuration, not data.

InputWhat it isWhere it lives
Synthetic recordsInvented patient/billing/clinical rows. Fake values, real structure. Seeded for reproducibility.data_synthetic/
Extraction tasksThree hand-written jobs — patient summary, ward census, medication review — each naming the minimum fields it needs and its lawful purpose.scripts/run_benchmark.py
The purpose policyThe rulebook: for care coordination, which data categories are necessary, 90-day retention ceiling, identifiers must be pseudonymised.compliance/policy.py

Nothing is downloaded. Nothing is scraped from a live system. There is no training set because there is no training.

One detail worth volunteering, because it sounds like a weakness and is actually a strength: the compliance rules never see a single patient value. Records reaching the scorer carry only their category tags — “this record contained a direct identifier and something clinical”. The benchmark inputs are therefore free of personal data by construction, which is what lets the same harness eventually run against real hospital data without the benchmark itself becoming a privacy liability.

06How the score is computed

Know this cold. “How exactly did you get 0.131?” is an easy question to ask and an embarrassing one to fumble.

Each of the seven rules returns a score between 0 and 1. The overall score is their weighted mean, skipping any rule that does not apply. All seven weights are currently 1.0, so today it is a plain average — but the weighting mechanism exists for when we can justify treating some principles as heavier than others.

Worked example — the unconstrained baseline, which scores 0.131:

RulePrincipleScoreWhy
DM-01Data minimisation0.67Pulled 6 categories, 4 allowed → 2 in excess → 1 − 2/6
LB-01Lawful basis0.00None declared
SL-01Storage limitation0.00No retention period, no deletion route
SS-01Security safeguards0.25Only transport encryption → 1 of 4
PL-01Purpose limitation0.00No specific purpose declared
NT-01Transparency / notice0.00No privacy notice on record
AC-01Accountability0.00No audit log, no named party, no processing record

(0.67 + 0 + 0 + 0.25 + 0 + 0 + 0) ÷ 7 = 0.131

And the middle technique, at 0.500: full marks on minimisation and purpose limitation, half on lawful basis (consent claimed, no reference), half on storage (retention fine, no deletion route), half on security (2 of 4), zero on notice and accountability. (1 + 0.5 + 0.5 + 0.5 + 1 + 0 + 0) ÷ 7 = 0.500.

The point of partial credit

Compliance is not binary in practice, and a pass/fail benchmark would put “forgot to write down the consent reference” in the same bucket as “collected financial records with no lawful basis whatsoever”. Graded scores let the instrument rank techniques rather than merely reject them — which is what makes it a benchmark rather than a checklist.

  2. Run the headline benchmark python scripts/run_benchmark.py

  3. Land the middle row ~20 seconds

09Cross-examination

The two questions in bold are the ones with real teeth. Answer both honestly — a panel rewards a known limitation far more than a bluffed strength.

QHow did you train your model? What dataset?

Nothing is trained and there is no dataset of examples. The scorer is deterministic Python. Later, an off-the-shelf language model will do the extraction, used through prompting and tool design rather than fine-tuning, and evaluated against synthetic data. The word “trained” on our Review-1 slide was our error and we are correcting it.

QSo this is just if-statements. Where is the research contribution?

The contribution is not the difficulty of the code, it is the instrument and what it makes possible. No existing extraction technique reports a compliance number, so compliance cannot currently be compared across techniques at all. We define the criteria as executable checks, express an extraction run as scoreable data, and produce a reproducible artifact. The simplicity is deliberate — an auditable benchmark should be simple enough that anyone can verify what it does.

QYou wrote both the good technique and the bad one. Isn't the comparison rigged?

That is a fair challenge and we will not overclaim. What the benchmark demonstrates today is that the instrument discriminates — it produces different, explainable scores for different behaviours, with every deduction traced to a reason. It does not yet prove our method beats a published one.

The unconstrained baseline is modelled on how techniques in the literature actually behave: optimised for coverage, no declared purpose, no manifest. But modelled is not measured. Running a third-party technique such as AutoScraper through the identical harness is exactly the Review-II deliverable, and it is the honest next step.

QWhat stops a technique from simply lying in its manifest?

Today, nothing — and that is a stated limitation. Two things soften it. First, some rules check observable output rather than claims: data minimisation counts the categories actually pulled, so a technique cannot claim minimisation while sweeping up financial records. Second, the direction of travel is to derive more of the manifest from instrumentation instead of declaration — observing TLS on the connection, confirming an audit log was written.

It is worth adding that declared records are how compliance auditing genuinely works — a record of processing activities is a declaration too. Our contribution is making that declaration machine-checkable and scoreable rather than prose.

QYour data is fake. Does the result mean anything?

The synthetic data exercises the pipeline; it is not the evidence. The rules score categories and manifests, and both are identical in structure whether the record came from our generator or a real hospital. Swapping in live data changes the values, not the scoring behaviour — which is precisely why the adapter boundary is built the way it is. Live access is secured on paper but not yet usable, and we chose not to stall the compliance work waiting for it.

QHow does this handle the fact that every hospital system is different?

Three ways. The data source sits behind an interface, so a new hospital means a new adapter and no downstream change. Records are normalised onto a five-layer model and the standards that carry them — HL7, FHIR, DICOM, ISO/IEEE 11073. And most importantly the rules score data categories, never vendor field names: one system's PatientID and another's MRN are both a direct identifier, and the rule is identical for both.

QWho decided which categories a purpose is allowed? Isn't that arbitrary?

It is a judgement, and we made it explicit rather than burying it. The policy sits in one readable table so a clinician, a lawyer or a data protection officer can inspect and challenge it without reading code — which is a stronger position than a system whose thresholds are scattered through the implementation. Validating that table against domain expertise is future work we will name in the report.

QWhy is the overall score a plain average? Are all seven principles equally important?

Almost certainly not, and we do not yet have grounds to claim a particular weighting. Equal weights are the honest default. The harness already carries a per-rule weight, so once there is a defensible basis — legal severity, or expert elicitation — changing it is a one-line edit and the whole benchmark re-runs.

QWhy India's DPDP Act rather than GDPR or HIPAA?

The deployment context is Indian hospitals, and DPDP 2023 is the binding law there. The seven principles we encode — minimisation, lawful basis, storage limitation, security, purpose limitation, notice, accountability — are common to modern data-protection regimes, so the harness structure ports to GDPR by changing the policy table rather than the architecture.

QWhy headless browser automation rather than an API?

Because hospital systems mostly do not offer one. Data staff actually use sits behind a login, in a rendered interface. A managed API would be the stable choice if it existed; for the systems in scope it generally does not, which is why credentialed browser automation is the realistic path and why the literature treats it as its own tier.

QIs scraping a hospital system even legal?

We are not scraping anything without permission. Access is credentialed and institutionally arranged, which is a different activity from scraping a public site. The project's entire premise is that lawfulness is a design constraint measured from the start — and the harness is what turns that claim into something checkable.

QWhy not have the language model score compliance?

Reproducibility and auditability. A benchmark must give the same score for the same input every time, and a language model does not. And a deduction has to be defensible to a regulator — “the model judged it non-compliant” is not. The model's place is extraction, where the problem is genuinely open-ended.

QHow will you score AutoScraper if you cannot run it against a hospital system?

The harness does not need the hospital. It needs the categories a technique pulls and the manifest it can substantiate. We can run a published technique against our synthetic source through the same adapter, record what it retrieves and what it declares, and score that. Running it against live data is a later refinement, not a prerequisite.

QWhat is actually finished, and what is not?

Finished: the seven-rule compliance framework, the policy layer, synthetic generation, the adapter boundary, three techniques, the benchmarking harness, 91 tests. Not started: the language-model extraction agent, and anything requiring live hospital data. We would rather state that plainly than imply more.

10Gaps worth volunteering

Naming these first costs nothing and buys credibility. A panel that finds a gap you hid marks you down twice.

  • One purpose is modelled. Care coordination only. The structure supports more; we have not designed the taxonomy.
  • Manifests are declared, not verified. The strongest attack on the design, and we have a roadmap rather than a fix.
  • Both techniques are ours. A published baseline through the same harness is the Review-II deliverable.
  • No live hospital data. Secured on paper, unusable in practice; the adapter exists so this changes nothing downstream.
  • Rule weights are equal and unvalidated. The mechanism exists; the justification does not yet.
  • The agent is not started. Build step 6, deliberately after the measurement layer.
  • Act section numbers are not pinned. Rules cite DPDP principles by name; exact citations belong in the report's references and are still to be verified.

11The deck contradicts the code

Fix before 02.09

The slides say “four executable rules” and “careless ≈ 0.2”. The code now has seven rules, and the real figures are 1.000 / 0.500 / 0.131 across three techniques. A panelist reading the slide and then watching the demo print seven rule columns is an avoidable cross-question.

Three edits are needed:

  • Proposed Solution slide — “four executable rules … minimisation, lawful basis, storage limitation, security safeguards” becomes seven, adding purpose limitation, notice and accountability.
  • Work Completed slide — “4 executable DPDP rules” becomes 7; the demo line becomes the three-technique result.
